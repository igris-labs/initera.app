# pm-app roadmap

## Product boundary

V1 is a local, offline desktop work manager for one named user with multiple workspaces, each containing multiple projects. It uses Vue 3, TypeScript, Vite, Tauri 2, and SQLite. No account, server, sync, or team collaboration is required. Names collected on first launch identify the local actor and first workspace; they are editable in Settings. The browser preview uses local storage and demo issues. The native app uses SQLite for workspaces, projects, planning nodes, issues, workflow, saved views, cycles, time entries, activity, and backups. Platform acceptance and the remaining gaps below still gate a V1 release.

The native data root is the user's Documents directory under `pm-app/`. It contains `workspace.sqlite`, `media/`, `staging/`, `backups/`, and `recovery/`. Resolve Documents through Tauri's native path API; never build a path from a hard-coded home directory. Show the chosen data location in Settings. If Documents is unavailable or unwritable, show a recovery choice before creating work; never silently switch roots. SQLite access and media operations stay behind native commands. A Documents folder may be synced by the operating system; simultaneous access to the live database is unsupported, and backup/export must use a consistent SQLite snapshot rather than a raw file copy.

This roadmap is the execution index. [V1 specification](research-data/docs/v1/README.md) defines detailed product and data contracts; [IPEX Design System](IPEX-Design-System-Canonical.md) defines visual rules. Current user direction takes precedence over older planning defaults. In particular, first-launch naming replaces automatic unnamed workspace initialization. Linear references guide density and interaction, while IPEX keeps its own corners and identity.

## Release rules

- Every feature ships as a vertical slice: entry point, keyboard path, persistent command/query, loading/empty/error states, and acceptance test.
- SQLite is the durable source of truth. Components call a typed application client; Rust services own validation and transactions. Demo data and local storage stay in the prototype/test adapter only. Start and due dates, issue relations, sub-issues, cycles, and rich descriptions belong to V1, not a later expansion.
- A user can create and switch between multiple workspaces; each contains many projects. Assign stable internal IDs to workspace, actor, projects, and issues. Scope project and issue identifiers, queries, preferences, and mutations by `workspace_id`. Teams and membership remain outside V1.
- No screenshot-only controls. If a control is visible, its behavior, focus path, and failure state must work.
- For each named V1 capability, match Linear's creation, editing, filtering, keyboard, and lifecycle behavior before calling that capability complete. Record any deliberate local-first difference in its acceptance test. Feature parity refers to the V1 capabilities below; cloud collaboration and integrations remain outside this local release.
- Keep `src/components/ui` generic; put issue, project, and workspace behavior in feature modules. Prefer VueUse for standard browser/reactivity behavior already covered by the dependency. Avoid new dependencies for native CSS, Vue, or platform behavior.
- Use IPEX semantic tokens in `oklch()` for authored colors. Typography: 12px secondary/compact controls, 14px standard content and controls; larger sizes only for clear headings. Check visual scale at 100% in both themes.
- Motion must explain a state change. Keyboard commands and frequent navigation respond immediately. Occasional overlays use short, interruptible ease-out transitions. Honor reduced motion. Measure input-to-first-frame and interruption behavior, not only animation duration.

## V1 delivery sequence

### 0. Platform and contracts

Pin renderer/native toolchain and check a clean clone. Complete custom frame controls on macOS and Windows, plus Linux compile/smoke status. Validate bundled SQLite FTS5, file locations, migration rollback, single-instance behavior, suspend/quit hooks, and packaged startup. Define `ApplicationClient` DTOs, typed errors, mutation receipts, workspace revision events, and browser test adapter. No UI component invokes SQL or arbitrary native commands.

**Gate:** packaged empty app opens offline; migration failure shows recovery without replacing existing data; command contract passes both renderer and Rust tests.

Initial native foundation: Tauri resolves `Documents/pm-app`, opens SQLite with foreign keys and WAL, creates media/staging/backup/recovery folders, rejects newer schema versions, and exposes bootstrap/save-identity commands. A second transactional schema migration adds workspace-owned projects with unique names and identifier prefixes, plus typed list/create commands. A third migration stores theme and issue display preferences per workspace. A fourth migration stores workspace-owned issues with internal UUIDs, stable public identifiers, project association, labels, dates, triage, and order. A fifth migration adds project summary, description, status, priority, start/target dates, and ordered milestones. Later migrations add rich text title fields, issue parent/start-date fields, archive state, issue activity, and workflow statuses. Existing versioned workspaces receive a consistent SQLite snapshot in `backups/` before migration. Native startup loads projects, issues, and workflow statuses before opening the workbench. Project creation and editing, including milestones in one transaction, and issue creation/editing/list, sub-issue hierarchy, board movement, archive/restore, comments, paged activity, and workflow edits now use native commands; browser preview retains local storage. macOS uses the native overlay titlebar and traffic lights, while Windows/Linux retain explicit window controls. A complete application client contract and the rest of the V1 issue domain remain open platform gates.

Schema versions 12–13 remove the single-workspace constraint and scope public issue identifiers to a workspace. The sidebar now creates and switches local workspaces, the Projects plus opens project creation, and the top-right action names issue creation. Switching waits for queued native issue and preference writes before reloading scoped data.

### 1. Local identity and durable workspace

Persist local actor, workspaces, theme, and display preferences in SQLite. First-run setup creates actor and first workspace in one transaction, validates nonempty bounded names, survives restart, and never repeats after success. Settings rename updates all shell references without changing IDs. The sidebar lists workspaces, the adjacent plus creates one, and switching loads its own projects, issues, and preferences. Provide recovery for initialization failure.

**Gate:** fresh setup, restart, rename, failed initialization, and migration from prototype data all have explicit outcomes.

### 2. Issue foundation

Implement issue create/read/update/archive/restore, unassigned capture, project assignment, stable identifiers, priority, workflow status, estimate, start date, due date, labels, sub-issues, issue links, blocking/blocked-by dependencies, and activity history. Create dialog, compact list, issue pane, fullscreen detail, property pickers, comments, and keyboard commands all use the same records. Protect drafts and report validation errors in place. Triage supports accept, decline, and reopen. Dependency writes validate same-workspace ownership, self-links, duplicate edges, and cycles; deletion retains historical activity without dangling active relations.

Workflow status parity: keep the status lifecycle category separate from its display name and icon. Support Backlog, Unstarted, Started, Completed, and Canceled categories; custom names, descriptions, colors, icons, default status, and ordering within categories. Preserve at least one status in each category. Include On Hold in Started by default. Status removal must either reject while referenced or require an explicit destination for affected issues; archived custom statuses remain readable on existing issues and can be restored. The board now edits these fields, and SQLite stores each workspace's workflow. Native writes validate categories and defaults, reject removal while referenced, and rename issue statuses with activity in one transaction. Cross-surface status selection and category ordering still need acceptance review.

**Gate:** create in any entry point, edit in detail, inspect list/board/triage, restart, and find the same data. Tests cover hierarchy cycles, status history, identifier allocation, and failure rollback.

Current slice: issue and sub-issue titles, descriptions, properties, parent links, start dates, due dates, and workspace-selected point, size, and time estimates can be created and edited from the workbench. Native SQLite stores parent links by internal ID and rejects self-parenting or descendant cycles; the preview adapter persists the same visible fields. Archive and deletion offer explicit child handling: include descendants, make them top-level, or move them under another active issue. Archived children can be restored as top-level issues. Issue creation, property changes, archive/restore, and comments are stored in a paged activity timeline. Triage has accept, decline, and send-back actions. Native issue records now retain entry and resolution timestamps across triage transitions, including re-entry; existing open triage records are backfilled from creation time. Date filters for those timestamps remain open. Related, duplicate, blocking, and blocked-by links persist in SQLite with same-workspace, duplicate, self-link, and dependency-cycle validation. Workflow categories now drive active/completed visibility and project progress.

### 3. Projects and planning structure

Build project index, create/edit dialog, overview, resources, project-specific identifiers, milestones, and optional mixed module/feature trees. Issues can attach to a project directly or to one node. Move preview explains identifier and association changes; commit moves atomically and keeps aliases searchable. Project progress counts unique issues. Use rounded property pills in creation flows; do not create decorative controls without behavior.

The project composer now creates and edits name, prefix, icon, color, summary, description, status, priority, local lead, start/target dates, labels, and milestones atomically. Milestone edits preserve IDs; project rename updates the route and visible issue associations. Issues and sub-issues can be assigned to a milestone from their project during creation or in issue details. A reviewed project move now includes the issue subtree, offers Keep or Regenerate identifiers, previews cleared milestone, structure, and incompatible cycle assignments, and commits aliases for old IDs. The issue context menu also copies a branch name based on the current identifier. Deleting a milestone clears its assignments. The workspace Projects index uses the same compact, full-width workbench layout as Issues and shows persisted projects, leads, and issue counts. The project Overview shows description, milestones, saved HTTP(S) resource links, issue completion, and a project update composer with a timeline. Status, priority, lead, dates, and labels edit in place using the same controls as issue details; the icon and color edit through a shared picker. The Issues tab uses the same project record. Native SQLite migrates existing projects to default icon/color and empty label/resource lists. Project updates and property-change history are stored in the activity timeline, with older native entries loaded in pages of 30. The Structure tab persists nested modules and features, enforces same-project hierarchy, and assigns issues to nodes. Node ordering and a dedicated node issue view remain open.

**Gate:** create project with milestones, nest module/feature in either order, move issues between projects, restart, and verify identifiers/progress/resources.

### 4. Retrieval, views, and board

One query model powers issue list, board, counts, filters, grouping, sorting, search, and saved views. Board drag changes status or priority with rank persistence; cancel/failed mutation restores both data and layout. Saved views persist scope, layout, filters, grouping, ordering, visible properties, and favorites. Search uses SQLite FTS5 with identifier aliases. Keep list and board data parity.

Saved view definitions persist in workspace-scoped SQLite records in the native app, with create, edit, duplicate, delete, restart, and workspace-isolation checks. The browser preview still uses local storage. Native issue list and board filtering use one SQLite query for current scope, triage, status, priority, project, project status, project priority, project labels, project lead, project milestone names, assigned issue milestones, issue labels, due-date presence, text, and advanced date/relation groups; command bar issue search uses the same workspace-scoped FTS5 index. Status, priority, project, project status, project priority, project label, project lead, project milestone, assigned issue milestone, and issue label filters accept multiple included and excluded values with OR within each include property and AND across properties, including saved views. Label, project lead, project milestone, and assigned issue milestone filters support empty-property choices. Advanced filters support before/after/between dates and relation presence with AND/OR rules inside groups. Current list/board counts and native saved-view index counts derive from the same query mapping. Query paging, relative date rules, and migration of prototype local-storage views remain open.

Lists with more than 200 matching issues use TanStack Virtual with stable issue keys. The 10,000-issue browser fixture verifies bounded mounted rows and scrolling to the final issue; separate large-list tests cover pointer reordering and drops into empty groups. Smaller lists retain their existing motion and Sortable interactions. A native 10,000-record fixture with representative descriptions and labels measured about 20 ms to read from SQLite and 108 ms to serialize 5.4 MB in the Rust test build; this is a measurement, not an end-to-end startup guarantee. Large boards skip per-card Motion layout observers and use browser content visibility while retaining Sortable movement. Native startup still loads all records and boards still mount all cards, so end-to-end native and board performance gates remain open.

The browser preview filter menu supports text, multiple included and excluded statuses, priorities, labels, and projects, no-label choices, due-date presence, and advanced date/relation groups. Values within an included property combine with OR, while properties and exclusions combine with AND. Selections appear as removable chips, and saved views retain structured criteria. Native list and board use one typed issue query. Match [Linear's filter behavior](https://linear.app/docs/filters): additional property-specific operators, quick matching, keyboard entry, and shareable main-filter URLs remain to be checked. Clear, remove, and edit actions must update results without changing the current layout.

| Filter surface from the reference | V1 data and behavior required                                                                                                                                                                                               |

| Status, priority, labels, project | Multi-value choices, include/exclude operators, empty-property choices, archived-label visibility, and persistent saved views.                                                                                              |

Milestone name filters match milestones on the issue's project; the separate Milestone filter matches the issue's assigned milestone by ID. |
| Content and links                 | Indexed title/description/comments and typed links or reference sources.                                                                                                                                                    |
| Subscribers, templates, cycles    | Add only when durable subscribers, template identity, and cycle membership exist.                                                                                                                                           |

The screenshot's AI filter, agent, agent session, and suggested label entries require separate capabilities and are not part of the single-user local V1. Do not display inactive menu rows for them.

**Gate:** save board view, drag an issue, reopen as list, search it, restart; every surface agrees. Test empty lanes, keyboard alternatives to drag, invalid saved filters, and 10k issue performance fixture.

### 5. Rich content and activity

Use a shared Tiptap Vue 3 editor for project and issue descriptions, with headings, lists, checklists, code, links, and inline images. Versioned JSON is the canonical content and extracted text supports search. Small local images are embedded in the validated JSON and SQLite snapshot, so their references and bytes commit together. Support safe HTTP(S) links, named project resources, paginated activity, and durable status/property history. Never render arbitrary HTML or expose raw filesystem paths.

The shared editor supports headings, lists, checklists, code, HTTP(S) links, and inline images through a button or paste. Project and issue descriptions store a versioned Tiptap JSON document alongside Markdown; older Markdown-only records remain readable and editable. Native writes validate the document shape, image MIME/data size, and links. New native PNG, JPEG, and WebP images up to 20 MiB and 40 megapixels are decoded, kept as immutable app-managed files in `media/` beside `workspace.sqlite`, and referenced by media ID in stored documents. PNG uploads use lossless recompression when smaller; JPEG and WebP uploads keep their already compressed source bytes. The editor resolves them when opened and shows an explicit missing-image placeholder if a managed file is unavailable; legacy embedded images remain readable. Browser preview still embeds images up to 1 MB. Rich issue comments persist their structured document as well as text. Native FTS indexes visible issue/project description text, project labels/resources, and issue comments in the same transaction as their writes. The command bar can use these indexes to find matching issues and projects. Comment results open the exact activity entry, including older comments outside the first timeline page; native lookup checks workspace and archive scope. Old unreferenced media and abandoned staging files are cleaned after a 24-hour grace period at startup and daily.

**Gate:** paste image, comment, edit, restart offline, and inspect the same content and actor/timestamps. Failed media commit leaves no broken reference.

### 6. Cycles and time

Support manual and recurring cycles across one or more projects, issue membership, closed snapshots, and explicit rollover policies: automatic, leave, or ask. Reconcile missed boundaries once on launch. Cycle creation, assignment, close, and rollover are V1 release gates. Add explicit issue timers, one-running-timer default, pause/resume/switch, manual entries, totals, and configurable exit/sleep behavior. Native service owns timers and scheduling, independent of renderer lifecycle.

Current slice: the workspace sidebar opens a Cycles page. Manual cycles and named recurring series persist in SQLite. Each series has a configurable 1–56 calendar-day duration, recurrence interval in calendar days (at least the duration), first start date, a fixed 12-cycle future horizon, selected project scope, IANA timezone, and local start time. Independent series can overlap. Native half-open UTC boundaries handle DST; reconciliation jumps over empty missed periods after long downtime, processes more than 100 stored elapsed cycles in resumable batches with progress, and rolls unfinished work into the next current or future cycle. Each cycle has a persisted rollover policy; manual cycles can designate an open successor. Closing captures a durable issue snapshot and one transition receipt. Ask policy presents eligible issues for selective move, and closed metrics remain frozen after issue deletion. Assignment rejects issues outside selected projects; changing scope rejects incompatible existing membership. Issue details expose a cycle picker, and the Cycles page shows current/upcoming/previous cycles with issue-count progress. Manual cycles retain explicit completion and rollover. Workspace settings offer Fibonacci, linear, exponential, T-shirt, and time estimates. Open cycles support title and description edits; future cycles can be rescheduled while preserving IDs and issue membership. Native issue detail supports one running timer per workspace, automatic switch/pause, manual entries with edit/delete, totals, and time entries that survive restart. A sidebar indicator links to and pauses the running timer from other routes. Archiving an issue pauses its timer. A native workspace Time tracking view shows totals by issue, archived history, running time, and links to active issues; it has a command-bar entry and keyboard route. Workspace settings choose pause or continue on exit or sleep. A native 30-second heartbeat and clean-exit marker cap paused-policy timers at the last heartbeat after a crash or a sleep gap over three minutes; continued timers remain running. Recovery produces a warning toast. Target-platform boundary tests remain open.

**Gate:** DST, sleep, crash, long downtime, duplicate reconciliation, overlap, and exit-policy tests pass on target platforms. No status change starts/stops a timer implicitly.

### 7. Data portability and release

Archive/trash restore rules precede backup. The native Settings page creates, lists, exports, imports, and restores self-contained ZIP backups containing a SQLite snapshot and managed images with per-entry checksums. Legacy SQLite-only backups remain readable when their images still exist in live storage. Import validates image contents against the snapshot's media records in staging; images enter live storage only during the journaled database/media swap. Legacy embedded images remain in the SQLite snapshot. Restore stages a request and restarts the app; startup applies it before renderer commands can open the database. A recovery copy and interrupted-restore marker protect the previous database and media directory together. Startup recovers the previous generation before checking a requested backup that may have disappeared, and refuses to create a new empty database if recovery cannot produce a complete live generation. A failed request leaves the live workspace available and reports the error in Settings. The portable format is a snapshot ZIP rather than the planned JSON entity collection format; import summaries and timer/cycle catch-up review still need release work. Local Rust tests and browser journeys pass, and a macOS `.app` bundle builds. The release workflow now requests macOS and Windows builds on CI. Clean-machine installer journeys, accessibility/keyboard audit, motion review, and target-platform timing tests still require acceptance. State Linux support only after smoke test.

**Gate:** full fixture roundtrip preserves relationships/content/search; interruption at every restore stage leaves one complete workspace; packaged app passes primary journeys.

## Architecture contracts

```text
route/page -> feature component/composable -> typed ApplicationClient
            -> Tauri command adapter -> Rust service -> SQLite repository
```

`src/components/ui` owns only reusable control semantics, sizes, variants, and focus styling. `src/components/common` owns frame/navigation. Feature modules own issues, projects, triage, views, cycles, time, and settings. Pinia stores cache acknowledged entities and UI preferences; local drafts remain isolated. Rust services serialize writes and emit revisions after commit. Shared IDs and DTOs prevent UI state from becoming the domain model. Migrate existing code toward this boundary by vertical slice; do not scaffold empty modules.

## Motion contract

Use existing IPEX easing/duration tokens as first source. CSS handles predictable overlay and pane entry. Use `motion-v` `AnimatePresence` only when keyed content presence/layout changes need coordinated exit/entry; use Sortable for board pointer drag and Vue state as the source of truth. Do not animate layout dimensions in busy lists. Hover changes remain immediate or brief; keyboard command menu and row selection remain instant. For theme changes, test a short `clip-path` reveal with View Transitions where supported, with direct update fallback and reduced-motion bypass. For tab switches, do not add a cloned accessibility tree merely for decoration; implement a clip-path indicator only if it materially improves selection clarity. Validate rapid toggles, Escape, drag cancellation, and focus restoration at 60fps capture.

This follows [purpose and frequency guidance](https://emilkowal.ski/ui/you-dont-need-animations), [design engineering rationale](https://emilkowal.ski/ui/agents-with-taste), and [clip-path technique](https://emilkowal.ski/ui/the-magic-of-clip-path). Linear's [redesign account](https://linear.app/now/how-we-redesigned-the-linear-ui) informs hierarchy, density, and semantic color relationships; it does not publish exact application motion values. Proposed timings and limits live in [Motion and Interaction](<research-data/Motion and Interaction.md>).

## Future, outside V1

Teams, membership, permissions, accounts, synchronization, collaboration, notifications, integrations, agents, and mobile/web clients require separate product and security contracts. Team scopes and authorization come after local workspace switching. Do not infer those features from visible Linear screenshots or add inactive controls now.
